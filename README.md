# Acquiring CRM API

## О проекте

Учебный проект системного анализа и разработки REST API для CRM-системы обработки заявок на подключение торгового эквайринга.

Проект демонстрирует работу с API-контрактом, валидацию данных, идемпотентность запросов, загрузку файлов и взаимодействие Backend с PostgreSQL.

**Цель проекта:** продемонстрировать навыки системного анализа и практическую реализацию отдельных сценариев API.

## Функциональность

Реализовано в локальном Backend:

- Создание заявки на подключение эквайринга.
- Валидация входных данных.
- Защита от повторного создания заявки с помощью `Idempotency-Key`.
- Загрузка вложений в формате PDF, PNG и JPEG.
- Ограничение размера загружаемого файла — 10 МБ.
- Сохранение метаданных вложений в PostgreSQL.
- Получение метаданных вложения по идентификатору.
- Скачивание загруженного файла.
- Обработка ошибок и возврат соответствующих HTTP-статусов.
- Проверка доступности API и подключения к базе данных.

Отдельно в проекте описываются бизнес-требования к ручной проверке ИНН, контролю доступа и аудиту операций. Наличие этих требований не означает, что соответствующая функциональность полностью реализована в Backend.

## API-эндпоинты

| Метод | Эндпоинт | Назначение |
|---|---|---|
| GET | `/health` | Проверка доступности API и подключения к PostgreSQL |
| POST | `/applications` | Создание заявки |
| POST | `/attachments` | Загрузка вложения |
| GET | `/attachments/{attachment_id}` | Получение метаданных вложения |
| GET | `/attachments/{attachment_id}/download` | Скачивание вложения |

Интерактивная документация доступна по адресу `/docs` после запуска локального сервера.

## Основные бизнес-правила

### Создание заявки

Обязательные поля запроса:

- `fullName` — ФИО клиента;
- `phone` — номер телефона;
- `inn` — ИНН;
- `source` — источник заявки.

Допустимые источники: `SITE` и `APP`.

Для защиты от повторной обработки используется заголовок `Idempotency-Key`:

- одинаковый ключ и одинаковые данные не создают повторную запись;
- повторное использование ключа с другими данными приводит к `409 IDEMPOTENCY_KEY_REUSED`;
- успешное создание новой заявки возвращает `201 Created`.

### Работа с вложениями

- Допустимые расширения файлов: PDF, PNG, JPG и JPEG.
- Максимальный размер файла: 10 МБ.
- Файл сохраняется в локальном каталоге `uploads`.
- Метаданные сохраняются в таблице `attachments` в PostgreSQL.
- Для каждого вложения генерируется уникальный `attachmentId`.
- Метаданные можно получить по идентификатору.
- Файл можно скачать по идентификатору.
- Если метаданные не найдены, API возвращает `404 Not Found`.
- Если файл отсутствует на диске, API возвращает `404 Not Found`.

**Ограничение текущей реализации:** проверка расширения и размера файла не заменяет проверку фактического содержимого, антивирусное сканирование и полноценную защиту загрузки файлов.

## Работа с PostgreSQL

В локальной реализации PostgreSQL используется для хранения заявок и метаданных вложений.

Основные таблицы:

- `applications` — сведения о заявках и ключах идемпотентности;
- `attachments` — идентификаторы вложений, имена файлов, пути хранения, типы содержимого, размеры и время загрузки.

Файлы хранятся в файловой системе, а не непосредственно в PostgreSQL. В таблице `attachments` хранится путь к файлу.

## Обработка ошибок

| HTTP-статус | Назначение |
|---|---|
| 400 | Ошибка валидации или некорректный запрос |
| 401 | Пользователь не авторизован — для сценариев с реализованной авторизацией |
| 403 | Недостаточно прав — для сценариев с реализованным контролем доступа |
| 404 | Заявка, вложение или файл не найдены |
| 409 | Конфликт идемпотентности |
| 413 | Превышен допустимый размер файла |
| 415 | Неподдерживаемый формат файла |
| 500 | Внутренняя ошибка сервера |
| 503 | Временная недоступность сервиса или базы данных |

Наличие статуса в таблице описывает предусмотренное или используемое поведение API, а не подтверждает реализацию каждого возможного сценария.

## Тестирование

Фактически проверены следующие сценарии:

- проверка состояния API и подключения к PostgreSQL;
- успешное создание заявки;
- повторный запрос с тем же ключом идемпотентности;
- конфликт при повторном использовании ключа с другими данными;
- ошибки валидации заявки;
- успешная загрузка PNG;
- отклонение неподдерживаемого формата;
- отклонение пустого файла;
- отклонение файла размером более 10 МБ;
- сохранение метаданных вложения в PostgreSQL;
- получение метаданных существующего вложения;
- ответ `404 Not Found` для несуществующего вложения;
- скачивание существующего вложения;
- ответ `404 Not Found` при скачивании несуществующего вложения.

Результаты проверок фиксируются в `TEST_RESULTS.md`.

## Запуск локального проекта

### 1. Установить зависимости

```bash
pip install fastapi uvicorn python-multipart "psycopg[binary]" python-dotenv
```

### 2. Настроить подключение к PostgreSQL

Создать файл `.env` в корне проекта и указать параметры подключения:

```dotenv
DB_HOST=localhost
DB_PORT=5432
DB_NAME=acquiring_crm
DB_USER=your_user
DB_PASSWORD=your_password
```

Заменить `your_user` и `your_password` собственными данными. Не публиковать `.env` в GitHub.

Перед запуском необходимо создать базу данных и таблицы, предусмотренные текущей реализацией.

### 3. Запустить Backend

В каталоге проекта выполнить:

```bash
python -m uvicorn main:app --reload
```

### 4. Открыть документацию API

- API: `http://127.0.0.1:8000`
- Swagger UI: `http://127.0.0.1:8000/docs`
- Проверка состояния: `http://127.0.0.1:8000/health`
