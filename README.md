# Acquiring CRM API

Локальный учебный REST API для прототипа CRM-системы обработки заявок на подключение торгового эквайринга.

## 1. О проекте

Проект моделирует часть бизнес-процесса обработки заявок на подключение эквайринга: приём заявок, сохранение данных в PostgreSQL и загрузку подтверждающих файлов.

Цель проекта — закрепить практические навыки системного анализа и разработки API-контрактов, а также продемонстрировать понимание HTTP, REST, SQL, идемпотентности, валидации входных данных и обработки ошибок.

**Статус:** учебный локальный прототип.

## 2. Реализованный функционал

- Проверка доступности API и подключения к PostgreSQL.
- Создание заявки на подключение эквайринга.
- Валидация входных данных.
- Идемпотентность создания заявок с использованием заголовка `Idempotency-Key`.
- Сохранение заявок и метаданных вложений в PostgreSQL.
- Загрузка файлов с проверкой расширения, размера и сигнатуры содержимого.
- Получение метаданных загруженного файла.
- Скачивание вложения по идентификатору.
- Обработка ошибок с соответствующими HTTP-статусами и кодами.

## 4. API-эндпоинты

Базовый URL: `http://127.0.0.1:8000`

| Метод | Эндпоинт | Назначение |
| GET | `/health` | Проверка состояния API и подключения к БД |
| POST | `/applications` | Создание заявки |
| POST | `/attachments` | Загрузка вложения |
| GET | `/attachments/{attachment_id}` | Получение метаданных вложения |
| GET | `/attachments/{attachment_id}/download` | Скачивание вложения |

Интерактивная документация Swagger UI доступна по адресу `http://127.0.0.1:8000/docs`.

## 5. Основные бизнес-правила

### Создание заявки

- Поле `fullName` обязательно; минимальная длина — 3 символа.
- Поле `phone` обязательно и проверяется по формату `+7XXXXXXXXXX`.
- Поле `inn` обязательно и проверяется по формату ИНН из 10 или 12 цифр.
- Поле `source` принимает значения `SITE` или `APP`.
- Дополнительные поля: `businessType`, `monthlyTurnover`, `averageCheck`, `city`.
- Для создания заявки требуется заголовок `Idempotency-Key`.
- Данные заявки сохраняются в PostgreSQL.
- При создании заявки присваиваются начальные значения `status = NEW` и `innVerificationStatus = PENDING`.

### Идемпотентность

Заголовок `Idempotency-Key` обязателен. Допустимая длина — от 1 до 255 символов.

Для предотвращения повторного создания заявок используется заголовок `Idempotency-Key`.

- **Новый ключ:** создаётся заявка, возвращается HTTP `201 Created`.
- **Тот же ключ и идентичные данные:** возвращается HTTP `201 Created` с данными ранее созданной заявки. Повторная запись в БД не создаётся.
- **Тот же ключ, но изменённые данные:** возвращается HTTP `409 Conflict` с кодом `IDEMPOTENCY_KEY_REUSED`.
- **Отсутствующий ключ:** возвращается HTTP `400 Bad Request` с кодом `VALIDATION_ERROR`.

Проверка формата ИНН реализована. Интеграция с ФНС и ручное подтверждение ИНН в текущем прототипе не реализованы.

### Работа с вложениями

- Поддерживаемые расширения: PDF, PNG, JPG и JPEG.
- Максимальный размер файла — 10 MiB (10 × 1024 × 1024 байта).
- Физические файлы сохраняются в локальный каталог `uploads`.
- Метаданные вложений сохраняются в PostgreSQL.
- Каждое вложение получает уникальный `attachmentId`.
- При загрузке проверяются расширение, размер и сигнатура содержимого файла.
- Метаданные доступны через `GET /attachments/{attachment_id}`.
- Скачивание доступно через `GET /attachments/{attachment_id}/download`.
- Если запись о вложении или физический файл отсутствуют, API возвращает соответствующую ошибку `404 Not Found`.
- При ошибках сохранения предусмотрена очистка физического файла или временных данных в соответствующих сценариях.

Проверка сигнатуры позволяет обнаруживать некоторые случаи несоответствия расширения и содержимого. Она не гарантирует полную корректность или безопасность файла. Полноценная проверка формата, антивирусное сканирование и система контроля доступа не реализованы.

## 6. Обработка ошибок

Основные реализованные коды ошибок:

| HTTP-статус | Код ошибки | Описание |
| 400 | `VALIDATION_ERROR` | Ошибка валидации входных данных |
| 400 | `EMPTY_FILE` | Загружен пустой файл |
| 400 | `INVALID_FILE_CONTENT` | Содержимое файла не соответствует ожидаемой сигнатуре |
| 404 | `ATTACHMENT_NOT_FOUND` | Вложение не найдено в БД |
| 404 | `ATTACHMENT_FILE_NOT_FOUND` | Метаданные существуют, но физический файл отсутствует |
| 409 | `IDEMPOTENCY_KEY_REUSED` | Один ключ идемпотентности использован с разными данными |
| 413 | `FILE_TOO_LARGE` | Размер файла превышает допустимый |
| 415 | `UNSUPPORTED_FILE_TYPE` | Расширение файла не поддерживается |
| 500 | `FILE_SAVE_ERROR` | Ошибка сохранения файла |
| 500 | `ATTACHMENT_METADATA_SAVE_ERROR` | Ошибка сохранения метаданных вложения в БД |
| 500 | `ATTACHMENT_METADATA_READ_ERROR` | Ошибка чтения метаданных вложения |
| 503 | `DATABASE_UNAVAILABLE` | База данных недоступна при проверке состояния API |
| 503 | `DATABASE_CONFLICT` | Не удалось разрешить конфликт записи при создании заявки |

Фактическая структура ответа зависит от обработчика ошибки. Ошибки валидации возвращаются в плоском формате, а некоторые HTTP-ошибки — внутри объекта `detail`.

Коды `401 Unauthorized` и `403 Forbidden` не относятся к реализованным сценариям текущей версии: авторизация и разграничение ролей пока не добавлены.

## 7. Структура данных

Для хранения данных используется PostgreSQL.

В проекте предусмотрено хранение:

- заявок на подключение эквайринга;
- ключей идемпотентности и исходных данных запросов, необходимых для предотвращения повторного создания заявок;
- метаданных вложений, включая идентификатор, имя файла, размер, тип содержимого и путь к файлу.

Физические файлы хранятся отдельно от метаданных в локальном каталоге.

Структура таблиц описана в `schema.sql`. Схему базы данных необходимо подготовить до запуска API. Автоматическое создание таблиц при запуске приложения не предполагается.

## 8. Тестирование

Проведено ручное тестирование API через Swagger UI, PowerShell, HTTP-запросы и SQL-запросы к PostgreSQL.

Проверены следующие сценарии:

- создание заявки и сохранение данных в БД;
- повторный запрос с тем же ключом идемпотентности;
- повторное использование ключа с изменёнными данными;
- обработка запроса без `Idempotency-Key`;
- сохранение данных после перезапуска API;
- загрузка корректного PNG-файла;
- отклонение неподдерживаемого формата;
- обработка пустого файла;
- обработка файла размером более 10 MiB;
- проверка граничного размера файла;
- проверка сигнатуры и несоответствия расширения содержимому;
- получение метаданных вложения;
- скачивание вложения и сравнение SHA-256 исходного и скачанного файлов;
- обработка отсутствующей записи в БД и отсутствующего физического файла;
- очистка физического файла при ошибке сохранения метаданных;
- проверка работы API после перезапуска;
- проверка неподдерживаемых HTTP-методов.

Подробные сценарии, результаты и замечания приведены в файлах `TEST_RESULTS.md` и `acquiring_api_attachment_test_cases.xlsx`.

Тестирование выполнялось вручную. Автоматизированный набор тестов и нагрузочное тестирование пока не реализованы. Результаты ручных проверок не заменяют полноценное тестирование безопасности и конкурентных запросов.
Конкурентное выполнение запросов с одинаковым ключом идемпотентности отдельно не тестировалось.

## 10. Запуск локально

### Требования

- Python 3.13 или совместимая версия.
- Установленный и запущенный PostgreSQL.
- Созданная база данных `acquiring_crm` либо другое имя, указанное в конфигурации.
- Подготовленные таблицы, соответствующие `schema.sql`.

### Установка зависимостей

Открой терминал в каталоге проекта и выполни:

```bash
python -m pip install -r requirements.txt
```

### Настройка подключения

Создай локальный файл `.env` в корне проекта. Можно взять `.env.example` за основу и указать свои параметры подключения:

```dotenv
DB_HOST=localhost
DB_PORT=5432
DB_NAME=acquiring_crm
DB_USER=your_db_user
DB_PASSWORD=your_db_password
```

Замени значения пользователя и пароля на свои локальные настройки. Не публикуй реальные пароли и другие секреты.

### Подготовка базы данных

Создай базу данных, если она ещё не создана, и выполни SQL-скрипт `schema.sql` в этой базе. Например, через `psql`:

```bash
psql -U your_db_user -d acquiring_crm -f schema.sql
```

Команда предполагает, что `psql` доступен в PATH и база данных уже создана. При необходимости используй полный путь к исполняемому файлу PostgreSQL.

### Запуск приложения

Из корневого каталога проекта выполни:

```bash
python -m uvicorn main:app --reload
```

После запуска открой:

- Swagger UI: `http://127.0.0.1:8000/docs`
- Проверка состояния: `http://127.0.0.1:8000/health`

Эндпоинт `/health` проверяет не только доступность приложения, но и подключение к PostgreSQL.

- ручное подтверждение ИНН с обязательным подтверждающим вложением;

- антивирусная проверка загружаемых файлов;
